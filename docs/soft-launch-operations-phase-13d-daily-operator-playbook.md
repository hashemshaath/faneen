# SOFT LAUNCH OPERATIONS — PHASE 13D
## Daily Operator Playbook + Reporting Templates

> مرحلة تشغيل فقط — لا تغييرات كود، لا DB، لا RLS، لا RPC، لا migrations.
> النطاق: جدة + الرياض · 5 قطاعات · 15–25 مزود · 30–50 عميل · 10–14 يوم مراقبة.
> الحالة السابقة: 13A READY · 13B ACTIVATION KIT READY · 13C DAY 0 BOARD READY.

---

## 1) Operator Mission

مهمة المشغّل اليومي خلال الإطلاق التجريبي:

- ضمان أن **كل RFQ جديد تتم مراجعته** خلال أقل من ساعتين من وصوله.
- ضمان أن **العميل لا يبقى بدون متابعة** لأكثر من 24 ساعة.
- ضمان أن **المزودين المناسبين يتم التواصل معهم** لكل RFQ صالح.
- ضمان أن **مشاكل الإرسال/الرفع/البحث تُسجّل فورًا** في Issue Log مع تصنيف الأولوية.
- ضمان أن **تقرير نهاية اليوم يصدر قبل نهاية الدوام** (قبل 7:00 مساءً).
- الحفاظ على **سلوك تشغيلي محايد**: لا وعود بأسعار، لا وعود بمدة تنفيذ، لا وعود بطلبات مؤكدة للمزود.
- توثيق كل قرار يومي (Continue / Fix / Pause / Expand) في التقرير.

## 2) Daily Schedule

جدول يومي ثابت — 5 نقاط تفتيش.

### 🕘 9:00 صباحًا — Health Check (≈30 دقيقة)
- فحص **RFQs الجديدة** منذ آخر تقرير.
- فحص **failed submissions / uploads** (سجل الأخطاء + console + edge logs).
- فحص **WhatsApp clicks** إن وُجدت إحصائيات (روابط wa.me).
- فحص **cron / email logs** (تذكيرات، إشعارات، تقارير مجدولة).
- فحص **طلبات مزودين Pending** بانتظار الاعتماد.
- النتيجة المتوقعة: لائحة مهام اليوم + أي إنذار P0/P1.

### 🕚 11:00 صباحًا — Provider Follow-up (≈45 دقيقة)
- متابعة **المزودين الذين لم يردوا** على دعوة الانضمام.
- متابعة **من بدأ التسجيل ولم يكمل** ملفه.
- طلب **الصور والخدمات الناقصة** لمن أكمل جزئيًا.
- تحديث حالة كل مزود في First Provider Cohort Board.

### 🕐 1:00 ظهرًا — RFQ Matching Review (≈60 دقيقة)
- مراجعة كل RFQ جديد منذ الصباح.
- تحديد **2–4 مزودين مناسبين** لكل طلب صالح.
- تسجيل **حالة المطابقة** ( Matched / Needs Clarification / Out of Scope / Test ).
- تحديد **next action** لكل RFQ ومالكه.

### 🕓 4:00 عصرًا — Customer Follow-up (≈45 دقيقة)
- متابعة العملاء الذين **أرسلوا طلبات** اليوم.
- متابعة من **بدأ ولم يكمل** الطلب.
- طلب **توضيح للطلبات الناقصة** (مدينة، قطاع، مواصفات).
- تحديث First Customer Pilot Board.

### 🕕 6:00 مساءً — Daily Report (≈30 دقيقة)
- تلخيص KPIs اليوم.
- تسجيل المشاكل المفتوحة والمغلقة.
- قرار اليوم التالي: **Continue / Fix / Pause / Expand**.
- إرسال التقرير لقناة العمليات قبل 7:00 مساءً.

## 3) RFQ Handling SOP

> دليل تشغيل فقط — لا يغيّر أي system statuses.

الخطوات لكل RFQ:

1. **استلام الطلب** (من Dashboard / إشعار).
2. **التحقق من جودة الوصف**: واضح؟ يذكر الغرض؟ يذكر الكميات/الأبعاد إن لزم؟
3. **التحقق من المدينة والقطاع**: داخل النطاق (جدة/الرياض + 5 قطاعات)؟
4. **التحقق من الملفات** إن وُجدت: تفتح؟ مقروءة؟ غير حساسة؟
5. **تصنيف الطلب** (تصنيف تشغيلي داخلي فقط):
   - ✅ واضح وجاهز للمطابقة.
   - 🟡 يحتاج توضيح من العميل.
   - ⛔ خارج النطاق (مدينة/قطاع غير مدعوم).
   - 🧪 اختبار / غير جاد.
6. **اختيار 2–4 مزودين** مناسبين من First Provider Cohort.
7. **متابعة رد المزود** خلال 24 ساعة.
8. **تحديث حالة الطلب** في لوحة المتابعة الداخلية.
9. **إغلاق الطلب** بأحد التصنيفات التشغيلية:
   - Matched
   - Contacted
   - Completed
   - Cancelled
   - Needs Follow-up

SLA تشغيلي مقترح:
- مراجعة أولية: < 2 ساعة عمل.
- مطابقة مزودين: < 4 ساعات عمل.
- متابعة العميل: < 24 ساعة.

## 4) Provider Follow-up SOP

| الحالة | ماذا نرسل | متى نتابع | متى نصعد | حركة Tier |
|---|---|---|---|---|
| جديد ولم يرد | رسالة WhatsApp تعريفية (من 13B) | بعد 24 ساعة | بعد 72 ساعة بدون رد | A → B بعد محاولتين |
| رد ولم يسجل | رابط مباشر للتسجيل + شرح مختصر | بعد 24 ساعة | بعد 48 ساعة | يبقى A |
| سجل ولم يكمل ملفه | تذكير بالحقول الناقصة (صور، خدمات، تغطية) | بعد 24 ساعة | بعد 72 ساعة | يبقى A |
| أكمل وينتظر الاعتماد | إشعار باستلام + مدة المراجعة | يوميًا داخليًا | بعد 48 ساعة بدون اعتماد | يبقى A |
| تم اعتماده | رسالة ترحيب + كيف يستقبل طلبات | عند أول RFQ | إذا لم يرد على أول RFQ خلال 24س | A |
| لا يستجيب للطلبات | تذكير لطيف + سؤال عن السبب | بعد 24 ساعة من كل RFQ | بعد طلبين متتاليين بدون رد | A → B بعد 2 · B → C بعد 3 |

ملاحظات:
- التصعيد = تنبيه قائد العمليات + تسجيل في Issue Log (نوع Operations).
- نقل Tier تشغيلي داخلي فقط، لا يغيّر أي حالة في النظام.

## 5) Customer Follow-up SOP

| الحالة | الرسالة المناسبة | وقت المتابعة | تسجيل الملاحظة |
|---|---|---|---|
| استلم الدعوة ولم يفتح الرابط | تذكير قصير + شرح القيمة | بعد 48 ساعة | Pilot Board → "Invited" |
| فتح ولم يبدأ RFQ | رسالة "هل تحتاج مساعدة في صياغة طلبك؟" | بعد 24 ساعة | "Opened, Not Started" |
| بدأ ولم يرسل | تذكير + عرض مساعدة | بعد 24 ساعة | "Drafted" + سبب التوقف إن عُرف |
| أرسل طلبًا ناقصًا | طلب توضيح محدد (سؤال أو سؤالين فقط) | خلال 4 ساعات عمل | "Needs Clarification" |
| أرسل طلبًا واضحًا | تأكيد استلام + متى يتوقع ردًا | فوري + متابعة بعد 48س | "Submitted" |
| تمت المطابقة معه | إشعار بأنه تم التواصل مع مزودين | يومي حتى أول رد مزود | "Matched" |
| انتهت التجربة | استبيان قصير (5 أسئلة) + شكر | خلال 48 ساعة من إغلاق الطلب | "Feedback Collected" |

القاعدة الذهبية: **لا وعود بسعر أو مدة تنفيذ**، فقط متابعة الحالة.

## 6) Issue Log Template

جدول مشاكل يومي (يُحفظ في Sheet مشترك):

| الحقل | الوصف |
|---|---|
| ID | `ISS-YYYYMMDD-NNN` |
| التاريخ | تاريخ الرصد |
| النوع | Technical / Operations / Business / UX / Data Quality |
| الوصف | جملة أو جملتين بالعربية |
| الصفحة/المسار | `/rfq/new`, `/dashboard`, ... |
| التأثير | عدد مستخدمين / RFQs متأثرة |
| الأولوية | P0 / P1 / P2 / P3 |
| المسؤول | اسم الشخص |
| الحالة | Open / In Progress / Blocked / Closed |
| الإجراء التالي | خطوة عملية محددة |
| تاريخ الإغلاق | عند الإغلاق فقط |

تعريف الأولويات:
- **P0**: تعطل وظيفة حرجة (submit/upload/login) أو شكوى خصوصية → تصعيد فوري.
- **P1**: تجربة مكسورة لمستخدم محدد، يوجد حل بديل → خلال 24 ساعة.
- **P2**: تحسين تجربة / مشكلة منخفضة الأثر → خلال أسبوع.
- **P3**: ملاحظة أو طلب مستقبلي → Backlog.

## 9) Quality Rules

قواعد جودة تشغيلية ملزِمة:

- ⛔ **لا يتم إرسال طلب لمزود** إذا الوصف غير واضح جدًا — يجب طلب توضيح من العميل أولًا.
- ⛔ **لا يتم اعتماد مزود** بدون صور وخدمات واضحة ومدينة تغطية محددة.
- ⛔ **لا نعد العميل** بسعر أو مدة تنفيذ — هذا قرار المزود حصرًا.
- ⛔ **لا نعد المزود** بطلبات مؤكدة — فقط فرص مطابقة.
- ✅ **كل متابعة تُسجل** في لوحة المتابعة (Provider/Customer Board).
- 🚨 **أي failure تقني** في submit/upload → Issue Log P0 + تصعيد فوري.
- 🚨 **أي شكوى خصوصية** → Issue Log P0 + تصعيد فوري للمسؤول.
- 📝 **كل رسالة خارجية** تُستخدم نسخها من 13B دون تعديل المحتوى الجوهري.

## 10) Final Daily Decision Rules

### 🟢 Green — Continue
- لا failures تقنية اليوم.
- RFQs واضحة وقابلة للمطابقة.
- مزودون يردون خلال SLA.
- لا شكاوى حرجة (خصوصية/أمان/بيانات).
- KPIs ضمن النطاق المتوقع.
- **القرار**: استمر بنفس النطاق، نفّذ خطة الغد كما هي.

### 🟡 Yellow — Fix
- completion rate منخفض (< 40%).
- zero-result searches مرتفعة (> 20% من البحث).
- بعض المزودين لا يردون (> 30% من Cohort).
- طلبات كثيرة تحتاج توضيح (> 50%).
- **القرار**: استمر، لكن ضع 1–3 إصلاحات تشغيلية محددة للغد، وراقب لمدة 48 ساعة قبل التصعيد.

### 🔴 Red — Pause
- submit/upload failure مؤكد ومتكرر.
- route broken (صفحة حرجة لا تعمل).
- شكوى خصوصية أو تسريب بيانات.
- أكثر من **يومين متتاليين بدون RFQs جديدة**.
- مزودون **لا يستجيبون نهائيًا** (> 70% من Cohort).
- **القرار**: أوقف الدعوات الجديدة، صعّد للقيادة، عالج السبب الجذري قبل الاستئناف.

### 🟣 Expand — Scale (شرط إضافي)
- 7 أيام متتالية Green.
- معدل مطابقة ≥ 60%.
- معدل رد مزودين ≥ 70%.
- لا P0/P1 مفتوحة.
- **القرار**: ناقش التوسعة في Weekly Review (مدينة/قطاع/حجم Cohort).
